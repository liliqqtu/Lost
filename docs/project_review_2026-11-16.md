## 范围与结论

检查了核心 GDScript、两章关卡、场景装配、存读档、战斗计算与执行、AI、救援、再移动、法杖/再动、支援、物品转移、动画及测试入口；扫描了 235 个脚本、场景、资源和工程配置文件中的静态资源引用。

已有按业务拆分的方向值得保留，但数据生命周期和异步行动流程还没有形成可靠边界。最优先的问题是进度保存不完整、治疗只改显示、攻击合法性缺失和终局流程缺口。建议先修正这些行为，再逐步重构；目前不建议整体推翻或继续大批扩充职业和技能。

这是代码审查加定向引擎复现，不代表已人工通关每条剧情或逐个检查全部动画美术。下文明确区分引擎复现和静态调用链确认。

## 已确认的问题

优先级：P1 为影响核心玩法、进度或使正常流程无法继续的问题；P2 为局部功能错误、边界风险或验证缺口。

### 1. [P1] 保存没有保存当前战局，跨章也没有继承角色成长

- 位置：`scripts/level_system_ui.gd:67`、`scene/level/level.gd:119`、`scene/ui/save_slot_menu.gd:259`、`scene/level/level_1/level_1.gd:102`。
- 手动保存只写章节和回合等摘要，不含角色等级/经验/属性、背包与耐久、装备、单位坐标、行动状态、事件进度、支援、运输队。读取后只切换场景，没有把战局恢复到场景中的入口。
- 例如第 5 回合保存后退出，再继续时会重新实例化章节、播放开场，从场景默认值开始；存档中的 `turn_count` 也没有回填。
- 即使不退出，序章切第一章也重新创建忒和伊萨尔，序章的升级、物品消耗与耐久变化不会继承。初始存档中的 `party`、`convoy` 空字段不构成实现。
- 建议区分“战役持久状态”和“章节中断状态”，建立完整的序列化/恢复契约；跨章先存队伍状态，再装配下一章。若只支持章首存档，必须保存章首队伍快照，并明确 UI 语义。
- 证据：静态调用链确认，仓库中没有对应战局反序列化流程。

### 2. [P1] 章节自动存档缺少读档使用的 `chapter_scene`

- 位置：`scene/level/level.gd:119`、`scene/ui/save_slot_menu.gd:259`。
- 序章通关存档记录了 `chapter_id = level_1` 和第一章名称，但没有 `chapter_scene`。继续游戏只读后者，缺失时回退序章。
- 因此卡片显示第一章，实际继续却进入序章。当前最后一章也没有独立的通关存档加载分支。
- 建议保存规范化章节 ID，并通过统一章节表解析场景和完成状态；或至少保证写入、读取同一个字段。
- 证据：静态调用链确认。

### 3. [P1] 治疗演出结束后真实 HP 没有恢复

- 位置：`scripts/battle_staff.gd:181`、`scene/ui/battle_animation_fx.gd:126`。
- 正常存在战斗场景时只执行 `play_staff_heal()`。该方法更新显示血量，但不更新 `target.hp`；真实 HP 的修改只存在于没有动画场景的兜底分支。
- 引擎复现：治疗前 HP 为 10、上限 20，治疗量 10；演出后显示 HP 为 20，真实 `target.hp` 仍为 10。随后仍会消耗耐久并获得经验。
- 建议治疗量和 HP 变更由领域逻辑结算，动画消费结算结果；有无动画必须得到相同的真实状态。

### 4. [P1] 武器损坏后仍执行预生成的追击/勇者打击

- 位置：`scripts/battle_combat.gd:44`、`scripts/battle_calculator.gd:106`。
- 序列生成后，执行每击前没有检查原武器是否仍可用；耐久归零虽然卸装，剩余打击仍使用序列中的旧伤害与命中。
- 引擎复现：武器耐久 1，单击伤害 10，攻击方可追击；第一击损坏后仍打第二击，总伤害为 20。
- 建议序列保留武器身份，每击验证存活、武器与耐久；损坏后停止该方剩余打击。预览也应考虑剩余耐久，避免显示无法执行的次数。

### 5. [P1] “不同 team”被当作敌对，绿色友军可被我方攻击

- 位置：`scripts/battle_unit_commands.gd:232`、`:269`、`:293`；`scripts/enemy_ai.gd:28` 也使用相同模型。
- 第一章雷恩、薇拉以 team 2 登场，玩家是 team 0；目前菜单、目标收集和攻击确认均使用 `team != selected_unit.team`，将他们当成合法攻击目标。
- 引擎复现：我方单位射程内只有绿色友军时，`_has_enemy_in_attack_range()` 返回 `true`。
- 建议统一阵营关系查询：`is_hostile()`、`is_allied()`，让战斗、治疗、救援、支援各自明确采用的关系规则，避免各处自行比较整数。

### 6. [P1] 法杖被当作普通武器，可攻击和反击

- 位置：`scene/character/units/unit.gd:150`、`scripts/weapon_select_menu.gd:153`、`scripts/battle_calculator.gd:90`。
- 射程查询和武器选择遍历全部 `Weapon`，没有排除 STAFF；反击只检查是否有武器和距离。回复之杖本身 `might = 10`，进入普通战斗会产生攻击伤害。
- 引擎复现：装备 STAFF 的防守方在邻接距离 `can_counter()` 返回 `true`。
- 建议区分攻击装备和辅助装备，统一实现 `can_attack_with()` 与 `can_counter_with()`。射程查询同时过滤装备资格；目前未过滤 `can_equip()` 的背包武器也会污染威胁范围。

### 7. [P1] 败北没有接收处理，正常失败后无法返回或重试

- 位置：`scripts/battle_manager.gd:338`、`scene/level/level.gd:82`。
- 我方全灭后设置 `battle_over`，阻断普通输入并发出 `defeat_occurred`，但没有关卡或 UI 连接该信号。关卡只连接胜利。
- 结果是玩家全灭后停留在失去控制的地图，不能通过正常界面重试或返回标题。
- 建议提供失败收尾流程，等待当前演出结束后展示重试/读档/返回标题，并确保输入路由仍可处理失败界面。
- 证据：信号定义、发出位置及全仓库订阅检索确认，未做完整实机败北操作。

### 8. [P1] 救援者死亡没有处理被携带单位

- 位置：`scripts/battle_manager.gd:290`、`scripts/battle_rescue.gd:164`。
- 救援把目标隐藏并移动到 `OFF_MAP_CELL`，保留双向引用；死亡移除只从 units 删除救援者并 `queue_free()`。
- 被携带者仍留在 units，保持隐藏、地图外坐标和对已释放救援者的引用。回合结束判断又跳过 `carried_by != null` 的单位，可能出现有我方存活却无人可操作、也不触发败北的局面。
- 建议死亡收尾统一处理携带关系，按照玩法决定原地放下或共同退场，并在胜负判断前恢复引用和占位不变量。
- 证据：静态调用链确认。

### 9. [P1] 新游戏/切换槽位不清理全局战役状态

- 位置：`scripts/save_manager.gd:119`、`scripts/support_store.gd:21`、`scripts/convoy_store.gd:26`、`scene/level/level_0/level_0.gd:179`。
- `start_new_game()` 只写 JSON，未清理运输队、支援值、等级和本章登场记录；读取槽位也没有恢复或替换这些全局数据。
- 同一进程中游玩旧档后返回标题，再新建或读取另一槽位，会沿用旧会话状态。序章的运输队初始化还会因仓库非空而跳过。
- 建议以一个战役会话对象负责新建、加载、清空与跨章；槽位是完整状态的替换操作。
- 证据：静态调用链确认。

### 10. [P2] 法杖预览传入的数组类型不匹配

- 位置：`scripts/battle_staff.gd:139`、`:148`；`scripts/battle_forecast.gd:44`。
- 传入的 `dummy_sequence` 声明为 `Array`，接收参数要求 `Array[Dictionary]`。
- Godot 4.7 引擎复现报错：`The array of argument 2 (Array) does not have the same element type as the expected typed array argument.`
- 建议使用正确的类型；辅助行为预览后续可以独立建模，避免把治疗量塞入攻击伤害字段。

### 11. [P2] 行动菜单的“保存”关闭界面后留下隐藏菜单状态

- 位置：`scripts/battle_unit_commands.gd:171`、`scripts/level_system_ui.gd:67`。
- 保存先关闭行动菜单，但状态仍为 `ACTION_MENU`、光标处理仍关闭。保存方法只展示提示，没有回到行动菜单或地图。
- 玩家接下来仍在操作隐藏菜单；从行动菜单进入返回标题确认后选择取消，也没有恢复原菜单。
- 建议弹窗/保存保留返回上下文，完成后显式恢复对应界面和输入状态。地图菜单发起保存的路径需要单独验证。
- 证据：静态调用链确认。

### 12. [P2] 再移动动画期间仍接受确认/取消，可能重入和提前结束

- 位置：`scripts/battle_canto.gd:28`、`:43`。
- 开始移动只关闭 cursor 的 `_process`，没有离开 `CANTO_MOVING` 或设置忙碌标记。关卡仍把按键转发给 `handle_input()`。
- 连按确认可重复启动 Tween、重复连接信号；动画中取消会调用 `_finish_canto()` 清空 selected_unit，原动画结束时回调仍会访问它。
- 建议区分再移动选点和移动执行状态；在启动异步工作前锁住命令输入，完成或取消时只收尾一次。
- 证据：静态时序确认，未做人工连按复现。

### 13. [P2] 背包实例化破坏已经装备的引用

- 位置：`scene/character/units/unit.gd:341`。
- `_own_inventory()` 先记录装备是否在包内，再替换包内每一个 Resource。若原装备本就在包内，后续分支不会将 `current_weapon` 重绑到复制品。
- 引擎复现：同一武器入包并装备后调用 `_own_inventory()`，`inventory.has(current_weapon)` 为 `false`。
- 当前预置角色多以 `current_weapon == null` 启动，因此这不是所有单位开局都会触发的问题；它会影响预装备实例、将来的存档恢复或先装备再入树的单位创建方式。
- 建议保存装备索引/物品实例 ID，复制后重绑；同时检查容量和孤立装备的处理。

### 14. [P2] AI 按背包射程选目标，却没有选择实际攻击武器

- 位置：`scripts/enemy_ai.gd:34`、`scripts/battle_phases.gd:116`。
- 决策使用背包全部射程，但伤害按 `current_weapon` 计算，计划只返回站位与目标，执行前也不换装。计算器没有阻止攻击方从非法距离发起攻击。
- 引擎复现：装备射程 1 的剑，背包另有射程 2 的弓；距离 2 时 AI 返回攻击目标，但实际装备仍是射程 1。
- 建议计划包含武器，并按候选武器计算收益；执行时重新验证站位、关系、射程、装备资格和耐久。

### 15. [P2] 自动化测试已有失效入口，“集成测试全通过”不覆盖真实行为

- `tests/test_item_lifecycle.gd:53` 无法解析数组断言，`:101` 引用已迁移资源；即使修正转换括号，删除中间武器后预期数组也应是 `[w31, w33]`。

- `test_runner.gd` 没有调度这些独立测试；其法杖测试直接执行 `ally.hp += actual_heal`，再动测试也直接重置行动状态，没有走生产确认流程，因而漏掉真实治疗和预览错误。

- `test_save_system.gd` 会删除真实 `user://` 第 3 槽。此次没有运行它；应改用隔离存储路径后再接入套件。

## 其他需要修正或明确的边界

1. **存档可靠性**：`save_manager.gd:74` 直接以 WRITE 截断唯一文件，没有临时文件替换或备份，也未验证写入后错误；故障时可能丢失旧档。建议临时写入、校验、替换并保留备份，读取时验证版本和关键字段，而非任意 Dictionary 都视为有效存档。
2. **时长累计错误**：`level.gd:137` 每次把进程启动以来的完整时间加到旧累计值，两章连续通关会重复计入前一章；手动保存又不累计时间。应由会话计时器记录增量。
3. **法杖/再动升级依赖画面对象**：`battle_staff.gd:200`、`battle_dance.gd:149` 把 `level_up()` 放在 `battle_scene != null` 内。兜底运行时经验可超过 100 却不升级。经验结算应独立于演出，并复用普通战斗的逐段升级流程。
4. **熟练度无法从默认值成长**：`unit.gd:427/439` 用同一个 `rank_*` 同时作为初始熟练等级和上限，首次查询就初始化到该上限，随后增长被同一阈值截断。若设计意图是可成长的武器熟练度，应拆开职业上限、初始经验和当前经验。
5. **移动加成未进入核心查询**：虽然有 `get_effective_move()`，正常选人、AI、威胁范围仍用 `unit.move`。新增移动加成技能/装备时会出现面板、再移动余额与实际可达范围不一致；应明确所有范围查询采用的属性来源。
6. **数据配置存在无效字段**：`data/class_data/cleric.tres`、`mercenary.tres` 等使用 `cap_def`，实际字段为 `cap_def_h`；前者不会控制当前守备上限。修女当前填写值恰与默认值一致，暂时掩盖了问题。建议资源校验检查未知属性和遗漏的默认成长配置。

## 建议的重构顺序

### 第一阶段：先恢复核心行为和测试可信度

修复第 1—10 项，补上跨章成长、保存后重载、治疗真实 HP、耐久中断、友军不可攻击、法杖不可反击、携带者死亡、败北返回、新建/跨槽隔离的回归场景。先让测试能发现这些错误，再推进后续功能。

### 第二阶段：建立战役状态和持久化边界

引入战役状态模型，按稳定角色 ID、物品定义 ID 和物品实例数据保存等级、属性、耐久、装备索引、支援与仓库。章节配置集中维护 ID、标题、场景与下一章。章中存档额外保存单位位置、行动、事件、招募、救援关系和回合状态；恢复关系时按 ID 重建，不保存 Node 引用。

物品建议区分不可变定义资源和运行时实例状态。当前 `duplicate()` 应先修好，不必立即大迁移；序列化契约明确后再决定是否拆类。

### 第三阶段：让规则决定结果，让动画负责展示

保留现有计算器/执行器分工，增加统一的攻击合法性查询和有明确字段的行动结果。伤害、治疗、耐久、熟练度、经验由执行器持有；动画按结果播放并报告演出完成。这样正常画面、无动画、加速和测试路径会得到相同结算。

普通战斗、法杖、再动共用经验升级服务和行动收尾。异步输入采用明确的“选择—执行—演出—收尾”状态；每次开始执行前阻止重入，结束后统一恢复界面上下文。

### 第四阶段：按状态所有权收紧模块，而不是只按行数拆文件

`battle_manager.gd` 当前 644 行，超过文档约定的 500 行；更实质的问题是子模块可以相互读写状态和私有字段，例如命令模块直接读取法杖/再动的 `_is_*_selecting`。

建议用明确的行动控制器接口处理目标选择和输入，通过统一上下文获取当前单位、地图与查询服务；移动执行独立负责路径、动画、完成信号和取消。优先逐步替换最容易出错的共享状态，不一次性重写全部门面接口。

交易逻辑仍直接 `insert()` 和交换 `inventory` 数组，未来应通过背包的移动/交换操作封装，实现完整校验与回滚，避免外部再次破坏装备绑定不变量。

### 性能优化暂缓项

寻路当前使用数组线性找最优项，障碍判断和单位查询也线性扫描。对现有小地图不应直接断言性能不足。扩图前记录范围计算/敌方决策耗时，再考虑格子占用字典、地形缓存、堆优先队列，以及按地图状态版本缓存威胁范围。

近期提交导入大量动画切片，优先补上资源管线校验：路径、非空动画、必需动作、循环标志、特效映射和来源记录。静态引用扫描未发现运行时文件引用的路径缺失，失效引用集中于旧测试；这不等于所有动作名称和演出时序都已验证。打包体积与冷启动应另做导出测量后再决定图集合并。
